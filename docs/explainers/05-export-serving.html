05 · Export & Serving

From adapter to something a car (or a 2019 laptop) can run — July 2026

Decision

Export path: merge → GGUF → Q4_K_M, all inside the training kernel

The LoRA adapter is merged into the fp16 base, converted with llama.cpp's convert_hf_to_gguf.py, and quantized to Q4_K_M — the quality/size sweet spot (~1.9 GB for 3B, runs comfortably in 16 GB RAM on CPU). Doing this on Kaggle means the laptop only downloads the final ~2 GB artifact, not a 6 GB fp16 model, and the Intel Mac never has to run the conversion toolchain.

Rejected: shipping the adapter only. Honest on-device demos don't require the user to own a GPU to merge weights.
Rejected: Q8/Q5. Bigger with no measurable win on this narrow, structured task; Q4_K_M's regression is caught by the eval harness if it exists.

Decision

The student system prompt is baked into the Ollama Modelfile

Callers send only the signals JSON. The 60-token prompt ships inside the model artifact (SYSTEM block), temperature is pinned to 0, and the ChatML template matches Qwen2.5's training format. The deployable unit is "model + contract", not "model + prompt engineering guide".

Decision

Serving validates the contract at the boundary, not inside the model

The FastAPI service (POST /coach) validates inbound signals with the same Pydantic models used everywhere else, and validates the model's output against the contract before returning it — a malformed model response is a 502, never silently forwarded. The LLM runtime is behind the same pluggable backend interface as the teacher, so the service is runtime-agnostic (Ollama locally, anything OpenAI-compatible in production).

On-device numbers

Filled after export: GGUF size, load RSS, tokens/s and p50/p95 latency on the 2019 Intel MacBook Pro, measured by cabin-copilot eval against the local Ollama model.
