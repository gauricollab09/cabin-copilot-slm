01 · Project Selection & Strategy

Decisions made before writing a line of code — 3 July 2026

Context and goal

Portfolio project for AI Engineer / ML Engineer applications, hard deadline of one weekend, built by an engineer with 8+ years in computer vision and driver-monitoring systems (DMS), including production prompt-engineering of an on-device LLM pipeline. Two projects were planned — one fine-tuning, one RAG.

Decision

Fine-tuning ships first, RAG second

The deadline attaches to the fine-tuning project ("real-world fine-tuning on the CV before the weekend"). RAG has no deadline pressure and is deferred.

Decision

The task: driver-signal → coaching-message generation

Fine-tune a small model to convert structured DMS signals (drowsiness, gaze, phone use, cabin state) into a strict-JSON coaching response, deployable on-device.

Why this beats the alternatives considered:

  • Interview defensibility. It extends the author's actual production domain (DMS + on-device LLM + prompt engineering), so every design question has an authoritative answer. A borrowed Kaggle project can't offer that.
  • No IP overlap. All data is synthetic, generated by a documented pipeline in this repo; thresholds follow public DMS practice (PERCLOS bands, gaze-off-road research), not any employer's system.
  • On-device story. Quantized 3B running locally is precisely the "efficient, private, on-device AI" theme the target roles care about.

Rejected: vision-LM fine-tune on a distraction dataset. Flashier and closer to the CV, but VLM training on a free T4 within a weekend has a high risk of ending half-done. Deferred to project #3.
Rejected: health-signals report generator. Medical-adjacent claims invite hard questions and the demo is less compelling.

Decision

Student model: Qwen2.5-3B-Instruct

Small enough for QLoRA on a free T4 and CPU inference after Q4 quantization; strong instruction-following baseline; open weights with a permissive research license; first-class GGUF/llama.cpp support. Llama-3.2-3B is the named fallback and the 1B variant is the emergency CPU-training fallback.

Decision

Pluggable teacher, three first-class backends

Data generation works with any of: Anthropic API (best quality), OpenAI API, or free/open models (Groq, OpenRouter, or a fully local Ollama server). One abstract backend, two wire protocols — the OpenAI-compatible protocol covers four of the five providers, so the free path and the paid path share one code path. This was an explicit requirement: anyone should be able to reproduce the dataset with whatever access they have, including none.

Compute plan under real constraints

The build machine is a 2019 Intel MacBook Pro — no Apple Silicon, no CUDA, 16 GB RAM. No paid API keys were available at project start. That forced an honest production-style constraint: the entire pipeline must run on free infrastructure.

Insight

The core thesis: fine-tuning as prompt compression

The teacher runs with a ~1,200-token engineered prompt (signal semantics, severity policy, voice rules, few-shot examples). The student is trained to reproduce that behaviour from a ~60-token prompt. On-device, every prompt token is latency — so the 20× prompt reduction is the product win, and the eval harness exists to prove the behaviour survived the compression.
