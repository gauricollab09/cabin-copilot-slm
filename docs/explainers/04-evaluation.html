04 · Evaluation

How to know the fine-tune actually worked — July 2026

What question is each metric answering?

MetricQuestionHow
Schema-pass rateCan a machine consume the output? Strict Pydantic validation of the JSON contract; the single most common SLM failure mode.
Safety complianceWould you put it in a car? The same eight deterministic rules that gated training data, now as a score. Rule-level breakdown shows which behaviours regressed.
Severity-in-bandIs the urgency calibrated? Response severity inside the scenario's ground-truth band (never seen by any model at eval time).
Pairwise judge win-rateIs it actually better, not just valid? An LLM judge picks between two anonymized responses per scenario.
Latency p50/p95 + footprintDoes the on-device claim hold? Measured on the 2019 Intel MacBook through Ollama.
Decision

Three-way comparison, chosen to kill the two obvious rebuttals

(a) Fine-tuned 3B + student prompt vs (b) base 3B + student prompt isolates what training added. vs (c) base 3B + full 1,200-token teacher prompt answers "couldn't you just prompt it better?" — the prompting-only alternative pays 20× the prompt tokens on every inference, so matching or beating it is the product win.

Decision

Held-out scenarios come from a different seed, not a split

The eval set (n=150, seed 101) is generated independently of the training scenarios (seed 7) over the same taxonomy — distributionally identical, zero overlap by construction, and stratified across all 15 cells including the rare critical ones a random split can starve.

Decision

Judge hygiene: anonymized, order-randomized, mechanical tie-breaks

The pairwise judge never sees model names; presentation order is shuffled by a per-scenario seeded coin flip (position bias is real and measurable); and scenarios where one side failed to produce parsable JSON are decided mechanically — a valid response beats a broken one without spending judge tokens. Judge temperature is 0.

Rejected: single-response 1–10 scoring for comparison. Absolute scores from LLM judges are poorly calibrated across runs; pairwise preferences are far more stable. (Single-sample rubric scoring is used upstream, but only as a data filter where miscalibration costs little.)

Decision

Baselines run before training finishes

Baseline numbers (b) and (c) depend only on the base model and the eval set, so they run early on the local machine. If the fine-tune later fails to clear them, the project's claim changes honestly — the harness is the arbiter, not the narrative.
